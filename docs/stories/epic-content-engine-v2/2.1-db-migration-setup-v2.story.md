## Description

As a developer implementing Content Engine v2, I need the database schema extended with the new strategic profile fields and content tracking columns so that the new setup wizard, forge engine, and rotation logic have the data they need.

The current `users` table only holds basic demographic setup fields (`target_audience`, `main_pain_point`, `voice_tone`, `user_prompt`). This story adds the full strategic profile (15+ new fields: niche, expertise, audience psychology, offers, content pillars, depth preference, etc.) plus two tracking columns on `sf_posts`.

This is the foundation that unblocks every other CE-v2 story.

## Tasks

### Task 1 — Create users table migration (024) ✅

Create file `supabase-migrations/024_setup_v2_user_profile.sql`:

```sql
-- Migration: 024_setup_v2_user_profile
-- Adds strategic profile fields for Content Engine v2.0

ALTER TABLE users
  ADD COLUMN IF NOT EXISTS niche TEXT,
  ADD COLUMN IF NOT EXISTS expertise_statement TEXT,
  ADD COLUMN IF NOT EXISTS transformation_before TEXT,
  ADD COLUMN IF NOT EXISTS transformation_after TEXT,
  ADD COLUMN IF NOT EXISTS audience_frustration TEXT,
  ADD COLUMN IF NOT EXISTS audience_desire TEXT,
  ADD COLUMN IF NOT EXISTS audience_objection TEXT,
  ADD COLUMN IF NOT EXISTS audience_awareness TEXT DEFAULT 'solution_aware',
  ADD COLUMN IF NOT EXISTS content_pillars TEXT[] DEFAULT '{}',
  ADD COLUMN IF NOT EXISTS primary_goal TEXT DEFAULT 'balanced',
  ADD COLUMN IF NOT EXISTS content_depth TEXT DEFAULT 'balanced',
  ADD COLUMN IF NOT EXISTS posting_frequency TEXT DEFAULT '2-3_week',
  ADD COLUMN IF NOT EXISTS avoid_topics TEXT,
  ADD COLUMN IF NOT EXISTS brand_personality TEXT[] DEFAULT '{}',
  ADD COLUMN IF NOT EXISTS offers JSONB DEFAULT '[]',
  ADD COLUMN IF NOT EXISTS setup_version INTEGER DEFAULT 1;

-- Add CHECK constraints (only if column was just created — safe to run again)
DO $$
BEGIN
  IF NOT EXISTS (
    SELECT 1 FROM information_schema.table_constraints
    WHERE constraint_name = 'users_primary_goal_check'
  ) THEN
    ALTER TABLE users
      ADD CONSTRAINT users_primary_goal_check
      CHECK (primary_goal IN ('grow_audience','generate_leads','direct_sales','build_authority','balanced'));
  END IF;

  IF NOT EXISTS (
    SELECT 1 FROM information_schema.table_constraints
    WHERE constraint_name = 'users_audience_awareness_check'
  ) THEN
    ALTER TABLE users
      ADD CONSTRAINT users_audience_awareness_check
      CHECK (audience_awareness IN ('unaware','problem_aware','solution_aware','brand_aware','most_aware'));
  END IF;

  IF NOT EXISTS (
    SELECT 1 FROM information_schema.table_constraints
    WHERE constraint_name = 'users_content_depth_check'
  ) THEN
    ALTER TABLE users
      ADD CONSTRAINT users_content_depth_check
      CHECK (content_depth IN ('shallow','balanced','dense'));
  END IF;
END $$;
```

### Task 2 — Create sf_posts tracking migration (025) ✅

Create file `supabase-migrations/025_posts_content_type.sql`:

```sql
-- Migration: 025_posts_content_type
-- Adds content type and depth tracking to sf_posts for rotation logic

ALTER TABLE sf_posts
  ADD COLUMN IF NOT EXISTS content_type TEXT,
  ADD COLUMN IF NOT EXISTS depth_level TEXT;

DO $$
BEGIN
  IF NOT EXISTS (
    SELECT 1 FROM information_schema.table_constraints
    WHERE constraint_name = 'sf_posts_depth_level_check'
  ) THEN
    ALTER TABLE sf_posts
      ADD CONSTRAINT sf_posts_depth_level_check
      CHECK (depth_level IN ('shallow', 'balanced', 'dense'));
  END IF;
END $$;

-- Existing posts with NULL content_type are treated as legacy — no action needed
```

## Dev Notes

### Data Model Context

Current `users` table key columns (from `supabase-migrations/002_user_personalization.sql`):
- `target_audience TEXT`, `main_pain_point TEXT`, `voice_tone TEXT`, `user_prompt TEXT`
- `highlight_color TEXT` (from 004)
- `setup_complete BOOLEAN`

New columns being added follow the same `ADD COLUMN IF NOT EXISTS` pattern used in existing migrations.

### Backward Compatibility Strategy

Per PRD §16: Users with `setup_version = 1` (old setup) continue to work. The forge services treat `NULL` values on new fields as fallback to legacy behavior (e.g., use `main_pain_point` as `audience_frustration` if null).

### Migration Naming Convention

Existing migrations are numbered sequentially: `001` → `023`. Next available: `024`.

### Supabase Execution

Migrations are run manually via Supabase SQL editor or `supabase db push`. Both files must be applied in order: `024` before `025`.

### Testing

- **Test location:** No automated test files needed — validation is schema-level.
- **Validation method:** Manual — run both migrations in a Supabase SQL Editor session (schema inspection or fresh instance).
- **Test scenarios:**
  1. Run `024_setup_v2_user_profile.sql` on a clean DB → verify all 16 new `users` columns exist.
  2. Run `025_posts_content_type.sql` → verify `content_type` and `depth_level` columns on `sf_posts`.
  3. Re-run both scripts → confirm idempotency (no errors on second run).
  4. Insert a `users` row without the new fields → confirm defaults applied correctly.
  5. Attempt to insert `primary_goal = 'invalid'` → confirm CHECK constraint rejects it.
- **Frameworks:** None — pure SQL validation via Supabase dashboard.
