# Story 1.7 — Access Policy Fixes

**Epic:** DS-TERMINAL — Design System v2.0
**Story ID:** DS-07
**Status:** Ready
**Priority:** Medium
**Complexity:** S (Small)
**PRD Reference:** `docs/prd/prd-design-system-v2.md` § FR-010
**Blocked by:** Story 1.6 (route renames must be done first to avoid stale guard paths)

## Description

As a user who receives a shared post link, I should be able to view the post without being forced to log in, because the home feed already shows these posts publicly. The current `AuthGuard` on `/posts/[id]` creates an inconsistent experience where public-facing posts can't be accessed directly via link without authentication.

---

## Acceptance Criteria

- [ ] **AC1** — `AuthGuard` is removed from `web/src/app/posts/[id]/page.tsx`
- [ ] **AC2** — `/posts/[id]` renders correctly for unauthenticated users
- [ ] **AC3** — No user-specific private data is exposed on `/posts/[id]` for unauthenticated users (review `actions.ts`)
- [ ] **AC4** — Authenticated users continue to see the same post view as before (no regression)
- [ ] **AC5** — The post page has `position: relative; z-index: 1` on its wrapper (renders above watermark)

---

## Tasks

### Task 1 — Read `/posts/[id]/page.tsx` and `actions.ts`

Before changing, understand:
- Where is `AuthGuard` applied? (wrapping the component, or via `useAuth` redirect?)
- What data does `actions.ts` fetch server-side?
- Is any data fetched based on `user.id`? (user-specific data should only render when authenticated)
- Does the page show download/share buttons only for the post owner?

### Task 2 — Remove `AuthGuard`

Find the `AuthGuard` wrapper in `web/src/app/posts/[id]/page.tsx` and remove it. The page should render the post content for any visitor.

```tsx
// Before (example):
export default function PostPage({ params }) {
  return (
    <AuthGuard>
      <ClientPostView postId={params.id} />
    </AuthGuard>
  );
}

// After:
export default function PostPage({ params }) {
  return <ClientPostView postId={params.id} />;
}
```

### Task 3 — Audit `actions.ts` for data safety

Read `web/src/app/posts/[id]/actions.ts`. The server action fetches post data from Supabase. Verify:

1. The query fetches from `sf_posts` by post `id` — this is public data (posts appear in the home feed)
2. No user credentials, payment info, or private profile data is fetched here
3. If the post doesn't exist → returns `null` → page shows "not found" state

If any user-specific data IS fetched (e.g., "is this my post?"), make it conditional on authentication state rather than blocking the entire page.

### Task 4 — Handle owner-specific UI conditionally

If the post page shows controls that are owner-only (e.g., "Delete", "Edit", download button), keep those hidden for unauthenticated users:

```tsx
const { user } = useAuth();
const isOwner = user && post.user_id === user.id;

// Render owner controls conditionally:
{isOwner && <DeleteButton />}
{isOwner && <DownloadButton />}
```

### Task 5 — Add z-index to post page wrapper

The post page wrapper div needs:
```tsx
<div className="relative z-[1]">
  {/* post content */}
</div>
```

## Dev Notes

- The Supabase RLS (Row Level Security) policies are the true access control layer. If `sf_posts` has RLS that allows public SELECT, the page is already safe for public access. If RLS only allows authenticated reads, the server fetch will fail for unauthenticated users — in that case, the RLS policy needs to be updated (OUT OF SCOPE for this story — flag it if discovered).
- Do NOT add a login prompt or CTA to the post page for unauthenticated users. It's a public view — show the content.
- The home feed (`/`) already shows all posts without auth — consistency is the goal here.

- [ ] No errors in console when loading post page as unauthenticated user
